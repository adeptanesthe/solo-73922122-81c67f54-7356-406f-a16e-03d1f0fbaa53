# 再生纸厂收料回测：两套最近质心分类器的错收 / 漏收对比

上传**入厂 CSV**（批号、入厂分钟、含水率、白度）和**化验 CSV**（批号、出单分钟、合格与否），
按“有记录的分钟”回放收料判级与化验回单，对比：

- **固定模型**：与另一套模型从同一份内置标注样本起步，质心永不更新；
- **自适应模型**：每收到一张回单就增量更新质心；同一批号的“改判”会**替换旧标签的训练贡献**；
- 到两类质心距离相等（含浮点容差）时，一律判**不合格**。

页面按“已回放的最新回单”实时列出两套模型各自的**错收**（判合格、实际不合格）
和**漏收**（判不合格、实际合格）批号。上传的两份文件先整体解析校验，
任一失败都不会替换当前回放，页面上的进度与名单原样保留。

## 1. Docker Compose 启动（推荐）

```bash
docker compose up --build
```

启动后打开：

- <http://localhost:8000>（主端口）
- <http://localhost:5000>（Flask 习惯端口，同样映射到服务）

## 3. 三分钟演示“改判”

1. 打开页面，点击 **“载入演示样例（可演示改判）”**
   （等价于直接访问 <http://localhost:8000/?sample=demo&run=1> 载入并跑完）。
2. 连续点击 **“单步推进到下一记录分钟”**，观察时间线：
   - 第 1 分钟：A01–A05 入厂，两模型同源于内置样本，判级完全一致；
   - 第 2 分钟：5 张回单把自适应质心拉向新料分布；
   - 第 3 分钟：**B01** 入厂——固定模型判“不合格”，自适应模型判“合格”；
   - 第 5 分钟：**A03 改判**（合格 → 不合格）。系统先从“合格”质心扣除
     A03 的向量贡献，再把它加入“不合格”质心，而不是把两张回单叠加；
     A03 随即进入两套模型的**错收**名单；
   - 第 6 分钟：与 B01 指标完全相同的 **B02** 入厂，在“先判级”阶段，
     自适应模型因 A03 改判后的质心而改判为**不合格**；随后才处理 B01=合格 的回单；
   - 第 8/9 分钟：C01 构成两套模型共同的漏收示例。
3. 跑完后的名单：

| 模型 | 错收 | 漏收 |
|---|---|---|
| 固定 | A03 | B01、C01 |
| 自适应 | A03 | C01 |

即自适应模型从 B01 上挽回了一次漏收；A03 因为入厂当时的判级被保留，
在最终改判后仍是两套模型的错收。明细表中 B01/B02 的对比可直接说明改判
对后续判级的影响，时间线中改判条目带红色“改判”标记。

另有 **“载入‘等距判不合格’样例”**（`sample=tie`）：TIE01 取初始两质心的
精确中点，距离相等，页面显示“等距→不合格”。

样例原文件在 [`samples/`](samples/)，页面也提供下载链接，可改着玩后重新上传。

## 4. CSV 格式与校验规则

入厂 CSV 必需列（表头兼容空格/单位/中英文别名）：

```csv
批号,入厂分钟,含水率,白度
A01,1,14.2,74.6
```

化验 CSV：

```csv
批号,出单分钟,合格与否
A01,2,合格
A03,5,不合格
```

- 编码：UTF-8（含 BOM）或 GBK/GB18030 自动识别；
- “合格与否”接受 `合格/不合格`、`是/否`、`1/0`、`true/false`、`pass/fail` 等；
- 分钟必须是整数（允许 `5.0`、`5分钟` 这类写法）；
- 入厂批号必须唯一：每批一条特征向量，回单才能按批号定位训练贡献；
- **同一 (批号, 出单分钟) 只允许一张回单**，重复即整份上传失败并提示行号；
- 同一批号在不同分钟可以有多张回单——后到的视为“改判”，最新一张为当前真值；
- 化验批号必须能在入厂 CSV 中找到（否则无法取特征更新质心）。

校验失败时接口返回 `400 {"ok": false, "error": "中文原因", "state_preserved": true}`；
网页表单提交则 303 跳回并显示红色错误条，**旧回放原封不动**。

## 5. 回放与对账口径

- 可推进的分钟集合 = 入厂分钟 ∪ 出单分钟，升序、去重；
- 每个分钟严格按：**先**用当前质心判该分钟所有入厂批次，**后**处理该分钟回单；
  因此同分钟到达的回单不会影响该分钟的判级（测试 `test_same_minute_*` 锁定该顺序）；
- 每个模型对每批的判级在入厂当刻固化，后续学习不会回溯改写；
- 错收/漏收只与“当前已处理回单中每批最新的一张”比较；改判到达后名单自动重算；
- 重置会用同一份已校验数据重建两套新模型，可反复演示。

## 6. O(1) 回单更新与改判替换

模型只维护每类的计数 `n_c` 与坐标和 `sum_c`，以及
`contributions[batch] = (label, x)` 这一份当前贡献：

```text
收到 batch 的新标签 new：
  若 contributions[batch] 存在旧标签 old：
      sum[old] -= x ; n[old] -= 1      # 替换：先撤旧贡献
  sum[new] += x ; n[new] += 1          # 再加新贡献
  contributions[batch] = (new, x)
```

单张回单是一次字典读写加常数次浮点运算，耗时与已化验批数无关；
质心即 `sum_c / n_c`。实测 `bench/bench_update.py`：

```text
 lab batches | avg us/update
       1,000 |          3.5
      10,000 |          3.5
     100,000 |          3.6
     200,000 |          3.6
```

改判后质心与“用全部当前标签从头重训”的结果一致（有测试断言到 1e-12）。

## 7. HTTP / JSON API

| 方法与路径 | 作用 |
|---|---|
| `GET /api/state` | 完整回放状态（分钟、名单、计数、各批判级/回单历史、质心、时间线） |
| `POST /api/upload`（别名 `/upload`, `/api/backtest/load`） | multipart 两份 CSV，或 JSON `{"inbound_csv": "...", "lab_csv": "..."}` |
| `POST /api/sample/load`，body `{"name":"demo"\|"tie"}` | 载入内置样例 |
| `POST /api/step`（别名 `/step`, `/api/replay/step`, `/api/tick`） | 推进一个记录分钟 |
| `POST /api/run`（别名 `/run`, `/api/replay/run`） | 直接跑完 |
| `POST /api/reset`（别名 `/reset`, `/api/replay/reset`） | 用当前数据重置 |
| `GET /?sample=demo[&run=1]` | 一键载入（并跑完）的演示网址 |

表单路由（`/upload`、`/step`、`/run`、`/reset`、`/sample/<case>`）执行后
303 跳回页面，因此没有 JavaScript 也能完整操作；带 `Accept: application/json`
或 `/api/` 前缀时返回 JSON。multipart 的字段名不挑剔：优先按字段名
（`inbound`/`lab` 等），再按表头识别，实在无法识别且正好两个文件时按顺序处理。

## 9. 已知边界 / 剩余事项

- 全局单回放状态面向单机演示，没有多用户会话隔离；如需多人同时回测，
  应改为按 session/任务 id 保存状态。
- 入厂批号按“一批一条特征”校验；若业务上允许同批多次入厂，需要再引入
  入厂事件 id 并调整训练贡献键。
- 散点图为轻量手写 SVG，未做大数据量（数万点）下的聚合/虚拟化。
- 本交付环境没有 Docker 守护进程，`docker compose up --build` 未在本机实跑；
  已用等价的 `gunicorn --workers 1 --threads 4 app:app` 实跑验证入口，
  并用解析器校验了 compose YAML，镜像构建步骤需在有 Docker 的环境最终确认。
